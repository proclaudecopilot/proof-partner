=== Proof Partner ===
Партньорска (affiliate) система за proofnutrition.eu.

== Инсталация ==
1. Изисква Proof Shrine ≥ 6.38.5 (белият списък за купони в абонаментните кошници).
2. Plugins → Upload → Activate. Таблото: WP админ → Proof Partner (fullscreen). Порталът за партньори: /partner.
3. Настройки → Бранд: име, фирма/ЕИК/адрес (за справките), лого (URL), цветове (по подразбиране Proof navy/cyan).
4. Пакети · Подновявания: правилата за EPACK офертите и Sublium подновяванията (виж долу).
5. Импорт купони: съществуващите Advanced Coupons кодове → партньори (кодът остава същият).

== Как работи ==
Едно правило: партньорски купон при checkout = комисиона. Lock при checkout (партньор, код, ставка се замразяват),
server-side gate „един партньорски код на поръчка", holding период, clawback при refund/cancel, нощна равносметка,
Telegram сигнали, портал с табло/статистики/справки, ранглиста, игра.

== Proof-специфичното (1.0.0) ==
* EPACK/Кутии: партньорските кодове минават през белия списък на Shrine (иначе EPACK ги маха).
* Правила за пакети (per оферта): „фиксирана сума € за поръчка" или „% върху пакетната част", + дали клиентът
  получава отстъпката от кода. Изключена отстъпка = кодът само атрибутира (правилно за фиксираните €99.90 оферти).
  Останалите артикули в същата поръчка са по ставката на партньора. Пакетът се разпознава по line item meta
  _pshrine_ins_scope (Shrine Insights) / order meta _pshrine_combo_snapshot.
* Sublium подновявания: Никога / Първите N / Докато е активен; отделна ставка (празно = както първата поръчка).
  Партньорът идва от lock-а на родителската поръчка на същия абонамент (_sublium_subscription_id).
  Еднократните поръчки — винаги само веднъж. Броенето „№k" гледа колко по-ранни подновявания вече са с комисиона.
* Импорт на купони: списък на WC купоните без партньор (Advanced Coupons ги пази като shop_coupon) → име + email
  (логин за портала) + ставка → партньор + mapping. ACFW условията (BOGO, cart conditions) не се пипат.

* ПРОПУСНАТИ ПОРЪЧКИ (SHAPEUP10: 9 поръчки, книгата виждаше част): три причини, всичките поправени.
  1) Engine-ът създаваше комисиона само при статуса-тригер (напр. Delivered). Поръчка, която отива направо

     Сега и фоновата мрежа ги вкарва като „изчакваща" (само поръчки, които реално носят партньорски код —
     SQL предфилтър, без тежки зареждания).
* При свързване на код / промяна на „следи се от" / „Провери": поръчките с кода ОТ датата нататък минават
  през engine-а веднага (`adopt_live_orders`), не чакат мрежата. Попъпът казва колко са проверени и
  колко нови реда има. Отказани/върнати/неуспешни не се пипат; задържаните стават „изчакваща" и се
  одобряват сами, когато поръчката бъде доставена/приключена.
