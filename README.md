# Proof Partner

Партньорска (affiliate) система на LOGADOR за proofnutrition.eu: купон при checkout = комисиона (lock), per-partner ставки, правила по оферти (комисиона/отстъпка/подновявания, глобални и лични), фиксиран договор по фактура + ROI, служебни пратки, портал /partner, импорт на купони.

## Нова версия
1. Вдигни версията на **двете** места в `proof-partner.php`: header `Version: X.Y.Z` и `define( 'PROOF_PARTNER_VERSION', 'X.Y.Z' );` (и `Stable tag` в readme.txt).
2. Push в `main`.

GitHub Action-ът прави `php -l`, zip с папка `proof-partner/`, тага `vX.Y.Z` и Release-а. Сайтът се обновява през LOGADOR GitHub Updater (mu-plugin; token в Settings → GitHub ъпдейти) → Plugins → Update now / auto-updates.

## 2.2.0 — абонаментна политика (Sublium): 10 % първа · 5 % подновявания · без бонус за клиента, per партньор; фикс на подновяванията

Човекът: „комисионата за /essentials или друг Sublium план: 10 % при първата поръчка и 5 % за последващите, без допълнителна отстъпка за абонамента; клиентът не получава нищо като бонус за абонирането — всичко да може да се променя per партньор."

- **Политиката** (`PP_Offers::sub_policy / policy_rule / global_policy`): за всеки абонаментен ред (`kind = sub`: EPACK пакет, Кутии, ръчна оферта **или извън оферти**) без изрично правило по оферта. Резолюцията става лично(вид) → лично(any) → глобално(вид) → глобално(any) → **политиката** (само за `sub`). Глобални стойности: настройки `sub_first_rate` (10), `sub_renewal_rate` (5), `sub_customer_discount` (`none` | `coupon`), `renewal_mode` (сега по подразбиране `forever`) + `renewal_n`. Лични: колони `partners.sub_first_rate`, `sub_renewal_rate` (NULL = глобалното), `sub_discount` ('' = глобалното). Миграция `proof_sub_policy_2_2` записва стойностите изрично при ъпдейта (стар `renewal_rate` → `sub_renewal_rate`, ако е бил число).
- **Отстъпката за клиента** (`woocommerce_coupon_get_discount_amount`): абонаментният ред с партньорски код получава 0 (без бонус), освен ако партньорът/глобалното е „по купона". Еднократните редове в същата кошница — както досега по купона. Sublium копира купона върху подновяванията със замразената при checkout отстъпка → без бонус и там.
- **Замразяване**: снимката при checkout (`_proof_partner_offer_rules`) носи политиката като правило (`source: policy` / `policy·partner`), включително `_regular|sub`. Сметката на първата поръчка е от снимката. **Подновяванията** се плащат по текущите условия на партньора (глобален режим/N, негов %) — замразена политика или „както глобалното" в правило = политиката; изрично правило с „първите N / винаги" остава както е.
- **UI**: Пакети · Подновявания → панел „Абонаменти (Sublium) · партньорска политика"; картата на партньора → Данни → Възнаграждение → ред „Абонаменти (Sublium)" (първа %, подновявания %, бонус за клиента) + чип 🔁 в hero-то; картите на офертите казват „🔁: абонаментната политика" при липса на правило; „По оферти" показва източник „абон. политика". REST: `GET/POST /partners/{id}` приема/връща `sub_first_rate`, `sub_renewal_rate`, `sub_discount` + резолвираната `sub_policy`; `GET/POST /proof/settings` — `sub_first_rate`, `sub_renewal_rate`, `sub_customer_discount`.
- **Фикс (критичен) — подновяванията на Sublium не се разпознаваха.** Плъгинът търсеше `_sublium_subscription_id`; Sublium пише `_sublium_wcs_subscription_id`, маркира подновяването с `_sublium_wcs_subscription_renewal = yes`, слага родителската поръчка като `parent` и я пази в `sublium_wcs_subscriptions.parent_order_id`. `PP_Proof::is_renewal / parent_lock / subscription_orders` четат тях (директен SQL по postmeta + HPOS; старите ключове са резерва). Sublium копира партньорския купон (coupon item) върху подновяването → `maybe_create_commission` го атрибутираше по купон като **първа** поръчка; `renewal_attribution` вече се включва и при налична атрибуция по купон и връща подновяване №k с политиката (k = 1 + по-ранните подновявания на абонамента с комисиона).
- **Шейкърът** (Proof Shrine 6.57.0): филтър `pshrine_cart_is_affiliate` → активен партньорски код в кошницата или уловен партньорски линк (`PP_Attribution::SESSION_LINK`).
- Тест: `php tests/sub-policy-test.php` (40 проверки, без WordPress).

## 2.1.1 — готов вход за мениджъра; фиксираните договори в процента; смяна на имейла на партньор

- **Готов профил за вход.** Миграция `seed_manager_login` (еднократно при ъпдейта): ако няма адрес за вход → `manager_slug = proof-mgr` (входът е активен); ако няма нито един портален профил → създава се потребител `proofmanager` (вид „мениджър“, 5 % от днешна дата) с **парола, генерирана на сайта** (`wp_generate_password`, не стои в кода). Тя се пази в опция `proof_partner_manager_seed` и се показва в wp-admin → Proof Partner → 🔑 Достъп до портала (само `manage_woocommerce`) в синьо каре с адреса и потребителското име, докато администраторът не я скрие („Записах си я — скрий“) или не я смени от „Редакция“ (тогава опцията се трие сама; трие се и при махане на профила). Профилът няма достъп до WordPress — само до Партньорската книга на `/partner/proof-mgr`.
- **Фиксираните договори по фактура влизат в процента на мениджъра** (`PP_Bonus::orders()`): редовете със статус `fixed` (0 € комисиона в книгата) се броят с целия си оборот като нетен оборот (няма комисиона за изваждане), само ако поръчката е доставена сега (при тях clawback не оставя сума в книгата, затова се гледа статусът на поръчката в WooCommerce).
- **Имейлът на партньора се редактира.** Той е логинът в портала и живее на WP потребителя, не в `partners` — затова досега нито админът, нито партньорът можеха да го сменят. Ново: `PP_Partners::set_email()` (валидация + проверка, че не е на друг профил, `wp_update_user`), REST `POST /partners/{id}` приема `email` (картата → Данни → „Email (вход в портала)“), порталът → Моите данни има поле Email.

## 2.1.0 — вход за мениджъра на /partner/<slug> + бонус за мениджъра (само процент)

Пренесено от ANSA Partner 5.13–5.17 (`AP_Manager` / `AP_Bonus`), **без еднократния бонус за нов партньор** — само процентът.

**1. Достъп до портала (wp-admin → Proof Partner → 🔑 Достъп до портала, само `manage_woocommerce`).** Адрес за вход `/partner/<slug>` (един за всички профили; порталът на партньорите на `/partner` не се пипа) + глобален ключ „входът е активен“. Профилите са WordPress потребители с роля `proof_partner_manager` (способност `proof_partner_manage` + `read` / `view_admin_dashboard`); всеки с `manage_woocommerce` я има автоматично, така че администраторите работят както досега. Два вида достъп (user meta `proof_partner_portal_type`): **Мениджър** трупа бонус, **Потребител** вижда книгата без бонус. Нов профил (WP потребител само за портала; при махане се трие) или достъп на **съществуващ** WP потребител (ролята се добавя, при махане пада само тя). Действия: Редакция · Спри/Пусни (спирането затваря сесиите) · 💶 Табло бонус · Махни достъпа.
- Входът (`class-pp-manager.php`): форма в стила на портала, приема **само** потребител с ролята (не е втори вход за админите), 5 грешни опита от един IP = 15 мин заключване + известие във фийда/Telegram, последният вход се пази (`proof_partner_manager_last_login`). Чист портален профил (само нашата роля) не влиза през wp-login и бива пратен от wp-admin към портала; спрян профил не влиза никъде. Страницата е no-cache/noindex; nonce-ът се освежава през admin-ajax `proof_pp_nonce`. Slug-ът се разпознава и по пътя на заявката, ако rewrite правилата не са опреснени.
- След вход мениджърът вижда Партньорската книга (`PP_App::render_front`, същото app.js) на същия адрес, с „⏏ Изход“; линковете към wp-admin (Настройки, Класически изглед) ги няма за него. Всички проверки за достъп до книгата (REST, wp-admin екрани, view-as/справки в портала, изплащания, оферти, пакети, selftest) са на `PP_Manager::CAP`.

**2. Бонус за мениджъра** (`class-pp-bonus.php`, условия на профила — user meta `proof_partner_manager_bonus`: `from` · `pct`, по подразбиране 5 %): **X % от нетния оборот на ВСИЧКИ партньорски поръчки от началната дата нататък, без край**, където нетен оборот = `base_amount` (стойността на продуктите след отстъпката на клиента, без доставка, нето от връщания) **минус комисионата на партньора**. Реализирана = **доставена** поръчка (в спечелен статус в WooCommerce сега): approved/paid редове + pending редове с доставена поръчка (периодът на задържане на партньора не отлага мениджъра); `[самопокупка]` чака одобрение; reversed не влиза; clawback след изплащане сваля базата пропорционално; напълно върната отпада; **фиксираните договори по фактура (редове `fixed`, 0 € комисиона) не влизат**. Сметката е жива върху книгата — записват се само изплащанията (`proof_partner_manager_payouts`: user_id, amount, until, note, created_by).

**3. Таблото „💶 Бонус“ в приложението** (`#/bonus`): мениджърът вижда своето („Моят бонус“ — в менюто само ако е вид „мениджър“); администраторът — всеки профил („Бонус мениджър“, селектор) и **отбелязва изплащане по банка** („изплатено до дата“, по подразбиране краят на предишния месец → сумата се попълва с дължимото до тази дата). Слипове: за изплащане / X % от нетния оборот / оборот на програмата / изплатено; таблици по месеци (с „изплатено“, ако краят на месеца ≤ последното „до“), по партньори (клик → картата) и изплащания (махане на грешен запис — админ). REST: `GET /bonus?manager=ID&until=YYYY-MM-DD`, `POST /bonus/pay {manager, until, amount, note}`, `POST /bonus/payouts/{id}/delete` (последните две само `manage_woocommerce`). BOOT: `isManager`, `isAdmin`, `bonusNav`, `logoutUrl`, `adminUrl`. Настройки: `manager_slug`, `manager_enabled`.
